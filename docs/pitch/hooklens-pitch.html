HookLens
Uniswap v4 hooks · open source

See what your liquidity is really exposed to.

HookLens reads a v4 hook's code and runs it on a fork. It then shows LPs and hook developers, with evidence, when a withdrawal can be blocked, a fee raised, or accounting changed.

The problem

Hooks are arbitrary code in the swap path

A hook can revert withdrawals, override fees, call oracles, take a cut of swap amounts (return deltas) or be upgraded. None of this shows up in the pool key.

LPs can't read Solidity

Deciding whether to deposit into a hooked pool today means trusting the deployer or reading the code yourself.

Developers have no v4-specific CI check

General Solidity linters don't understand hook permissions, return deltas, or the PoolManager lifecycle.

All four share one analysis engine (the hooklens Python package), so a finding has the same ID everywhere.

Under the hood

Address / source→Resolve & compile→Permission bits→10 analyzers→6 fork scenarios→LP math→Evidence-checked AI→Reports

Deterministic analyzers

Permissions, access control, dynamic fees, oracles, external calls, withdrawals, accounting and return deltas, upgradeability, bytecode, source integrity.

Real execution

Foundry scenarios against the real PoolManager on a fork: withdrawal failure, oracle failure, fee escalation, admin and upgrade, accounting invariants, ordering.

Exact LP math

Integer ports of TickMath, SqrtPriceMath and LiquidityAmounts, checked against vectors generated by forge. Every figure is tagged on-chain, measured, hypothetical or unavailable.

Honest by design

Static findings are "inferred" and fork results are "observed". AI text that cites unknown evidence is rejected. HookLens never claims a hook is safe.

Run it

Start everything locally

Needs Git, Foundry 1.9, Python 3.11+ with uv, and Node 22.11+. On Windows, run the .sh scripts in Git Bash. Use three terminals.

One-time setup

git clone https://github.com/vipinraj32/HookLens && cd HookLens
git submodule update --init --recursive
(cd contracts && forge build)
(cd backend && uv sync)
(cd frontend && npm ci)
cp .env.example .env     # optional: mainnet/Sepolia RPC, Etherscan key, Anthropic key

Terminal 1: local chain and fixture hooks

scripts/dev-chain.sh
# → Anvil on http://127.0.0.1:8545, fixture hook addresses in contracts/deployments/31337.json

Terminal 2: API

cd backend
uv run uvicorn app.main:app --port 8000
# → health check: http://127.0.0.1:8000/v1/health   ·   worker: /v1/health/worker

Terminal 3: web UI

cd frontend
npm run dev
# → open http://localhost:3000

CLI (no server needed)

pip install "hooklens @ git+https://github.com/vipinraj32/HookLens#subdirectory=packages/hooklens"

hooklens scan ./contracts --local --html report.html
hooklens scan https://github.com/uniswapfoundation/v4-template --html template.html
hooklens scan ./contracts --json r.json --sarif r.sarif --fail-on high
Before the meeting: start all three terminals 10 minutes early, scan the oracle fixture once so solc is cached, and pre-generate report.html and template.html. Cloning v4-template takes about 90 s, so don't do it live on conference Wi-Fi. Open the HTML files from disk.

Full workflow

End-to-end demo (about 12 minutes)

Each step lists what to do, what appears on screen, and a line to say. The demo uses HookLens's own deliberately flawed test fixtures on a local Anvil chain. Say so up front.

Demo timer 00:00

Act 1: the LP's question (web app)

  1. Open the landing page at localhost:3000 and scroll to "Decode any hook address". Click the Oracle-gated withdrawal preset. You'll see beforeRemoveLiquidity (bit 9) light up in amber: it can block withdrawals. "A v4 hook's address tells you which callbacks run. This one runs before every withdrawal. The bits tell you that it runs, not what it does. So we look inside."
  2. Click "Scan a deployed hook", choose Local Anvil, paste the oracle hook address, and click Scan. Live progress: resolve, pin block, read code, match source, discover pools, run analyzers.
  3. Hook intelligence page. Show the identity (block, code hash, source status), the permission bits, and the findings. 4 medium findings: the withdrawal can revert, it depends on an external oracle, it makes external calls, and privileged config influences the callback. "Every finding points at the exact source lines. This one says: if the oracle is stale or returns zero, LPs can't withdraw."
  4. Open a finding and its evidence. Show the excerpt, the LP implications, and the "inferred" label. "This is inferred from code. Next, we prove it."

Act 2: prove it on a fork (Adversarial lab)

  1. Open the Adversarial lab and run Withdrawal failure. Foundry forks the chain and deploys routers against the real PoolManager. It adds and removes liquidity, then repeats under each detected condition (stale oracle, zero price, oracle revert).
  2. Show the steps and traces. In a verified run on the oracle fixture, the scenario ended unexpected_revert with 4 LP expectations not met: Adding liquidity, swaps, partial and full removal, and re-adding all passed. Removal was blocked under each oracle condition: oracle call reverts → mocked oracle revert; price 0 → InvalidOraclePrice(answer=0); price −1 → InvalidOraclePrice(answer=-1); stale → StaleOraclePrice(…, maxStaleness=3600). Removal recovered after each condition was lifted. Every step shows expected vs. observed, the decoded call tree, and a forge test reproduction command. "That's no longer a static guess. It's an observed revert, at this block, with a command anyone can re-run."
  3. LP exposure. Enter a position and show principal, divergence vs. hold, and the scenario effect, each with its tag. "We never blend measured and hypothetical numbers. If fee income wasn't measured, it says 'unavailable'."
  4. Generate the report. Download the JSON (with content hash) and the PDF.

Act 3: the developer's side (CLI and CI)

  1. Terminal: run hooklens scan ./contracts --local --fail-on high. It finds 6 hook contracts and 29 findings (8 medium, 10 low, 11 informational), and the gate passes because nothing is high. "Same engine, no server, no keys. Point it at source and it finds the hooks itself: mocks, tests and interfaces are skipped, with reasons."
  2. Open the pre-generated report.html: filter by severity, search "oracle", expand a finding, jump to the source.
  3. Real-world repo: open template.html from hooklens scan https://github.com/uniswapfoundation/v4-template. Counter is detected as a hook with only an informational finding (its enabled callbacks). "On a clean template it stays quiet. We fixed a false positive on onlyPoolManager exactly because we tested on this repo."
  4. Show the Action YAML (landing page → Products → GitHub Action). Explain SARIF in Code Scanning, the PR comment, and fork safety. "Every hook PR can be checked against v4-specific rules, with alerts on the exact line."

Close

  1. "What HookLens is not" slide or section: not an audit, not a forecast, no keys. "We'd rather be useful and honest than impressive. A clean report never means 'safe'."

If something breaks live

Scan stuck or API down
Check http://127.0.0.1:8000/v1/health/worker. Fall back to the scan you completed before the meeting (Dashboard → recent scans).
Simulation fails with infra_error
Usually Anvil restarted, so the fixture addresses changed. Re-run scripts/dev-chain.sh, then re-scan. Or show the pre-run simulation.
Network is slow
Skip live GitHub cloning; open template.html from disk. Everything else runs locally.
Pitch script

For the Uniswap team (about 5 minutes, then demo)

  1. Hook (30 s) "v4 made pools programmable. That's the point, and it's also the new risk surface: a hook sits in the path of every swap and every withdrawal. Today an LP can't tell whether a hooked pool can lock their funds, change their fee, or take a cut of a swap without reading Solidity."
  2. What we built (60 s) "HookLens is an open-source tool that answers one question: what is my liquidity really exposed to? It decodes the hook's permissions, runs deterministic v4-specific analyzers over the code, and then executes adversarial Foundry scenarios against the real PoolManager on a fork. Every claim links to evidence: source lines, bytecode, on-chain state, or a simulation step."
  3. Two audiences, one engine (45 s) "For LPs and integrators there's a web app: paste an address. For hook developers there's a CLI and a GitHub Action that run the same engine on source code in CI, with SARIF in Code Scanning. The finding IDs are identical in both, so a developer's CI and an LP's due diligence speak the same language."
  4. Why trust it (45 s) "It's built to be honest. Static results are labelled inferred, fork results observed. LP numbers are tagged measured or hypothetical and never blended. The AI layer is optional, and its output is rejected if it cites evidence that doesn't exist or invents numbers. And we never call a hook safe."
  5. Demo (8–12 min): follow the Full workflow tab.
  6. The ask (45 s) "Three things would make the biggest difference. First, feedback from your team on the rule set, especially return deltas and dynamic fees. Second, a path to surface this where LPs make decisions, for example as a signal next to hooked pools. Third, introductions to hook teams who'd run the Action in CI. It's open source, so you can try it today."

Why it matters for Uniswap

Safer hook adoption

LPs are more willing to provide liquidity to hooked pools when the risks are explained with evidence.

Better hooks, earlier

Hook developers catch withdrawal blockers and unbounded fees in the PR, before deployment.

Shared vocabulary

Stable rule IDs (HL.WDR…, HL.FEE…) give LPs, devs and reviewers one language for hook risk.

Open and reproducible

Every simulation ships a reproduction command; every report carries its block, code hash and limitations.

Q&A prep

Likely questions, honest answers

Is this an audit replacement?
No. It's a deterministic first pass and an execution harness. It finds and demonstrates specific v4 risk patterns with evidence. It doesn't prove the absence of bugs, and it never says a hook is safe.
How accurate is it? False positives?
The rules are heuristic and will have false positives and negatives. We test them against fixture hooks that include a deliberate false-positive case, and against uniswapfoundation/v4-template (where we found and fixed an onlyPoolManager false positive). We don't have a benchmark across many production hooks yet; that's a good next step, and help from your team would make a difference.
Which chains?
Ethereum mainnet, Sepolia and local Anvil. Adding a chain is server configuration: the PoolManager address and an RPC endpoint.
What if the source isn't verified?
Permissions and bytecode analysis still run (selectors, DELEGATECALL, admin selectors, proxies). Source-level rules are reported as not applicable rather than guessed.
Does the simulation touch mainnet?
No. Everything runs on a local fork. Privileged actions are impersonated inside the fork only. No keys or wallets are needed.
What does the AI do, and can it hallucinate?
It writes plain-language explanations from the deterministic evidence. A validator rejects output that cites unknown evidence, lines outside the evidence, runs that didn't happen, numbers not in the data, severity changes, or claims of exploitability or safety. It's optional; everything works without it.
Is it production-ready?
The engine, CLI and local stack are tested (backend, CLI package, forge, frontend unit and Playwright e2e). Not yet done: Docker images haven't been built and run, GitHub Actions workflows haven't run on GitHub, no license has been chosen yet, and the PyPI name "hooklens" belongs to another project, so we install from Git.
How is it different from Slither or other linters?
It's v4-specific: it understands hook permissions and address bits, return deltas, the PoolManager callback lifecycle and LP impact. And it executes scenarios on a fork instead of only reading code.
